# Blog builder

This script and Jenkins pipeline are built separately from my blog source, ideally it will stay separated and referenced via Jenkins, so it triggers the build and publishing process accordingly. The automation can trigger by leveraging webhooks, scheduled runs or manual triggers, whatever is defined by the Jenkins' workflow.

I am publishing this because I want it to be useful beyond my own blog and because my blog sources are private since I like to edit and change my project structure constantly.

To trigger the build it just needs:

a) A source with all the markdown files. In this case, my blog has a simple structure:

```
myblog/
│── main.css
├── img
│   └── favicon.ico
├── index.md       # this is the landing page; this sets <in_main to true>
├── posts
│   ├── ...
│   ├── 2025       # markdown files in these directories are the content; these set <in_post to true>
│   └── 2026
├── robots.txt     # you want this to toss away those pesky AI crawlers
├── snippets
└── templates
    ├── footer.html.j2
    ├── header.html.j2
    └── menu.html.j2
```

b) There are some environment variables needed to run the script:

* `BASE_URL`      This is the Codeberg pages URL for my user
* `SRC`           This is the path to my source repository
* `DEST`          This is the path to my pages repository, defaults to "../pages"
* `YEAR`          This is the current year, defaults to the Year (yyyy) in the machine
* `YEAR_LOOKBACK` Years to look back, for my blog, it should be 1, so it builds from 2025 until 2026. Defaults to 1

These are defined in the Jenkinsfile as well, so pretty much all that I need to publish, it is controlled by these variables.

c) If new directories are added, they need to be mapped by the `STATICS` dictionary in `blog_builder.py (40)`. `STATICS` is a map of paths and extensions, this tells the build process from where to take the sources and what files are to be taken; to do this, we may use environment variables to do this as well.

In the following example, we can add the `/extras` directory, where only `.txt` files are meant to be published:

```
    STATICS = {
        f"{SRC}": env_list_as_tuple("STATICS_BASE", (".txt", ".css")),
        f"{SRC}/img": env_list_as_tuple("STATICS_IMG", (".png", ".svg", ".ico")),
        f"{SRC}/extras": (".txt",),
    }
```

To achieve the same, we may just declare an environment variable:

```
export STATICS_EXTRAS=".txt"

# if I have more dirs in the path, then STATICS_A_B_C would be converted to {SRC}/a/b/c in the map
```

In this example `env_list_as_tuple` serves to pass a list of text like `"a,b,c"` as environment variable so it loads into the map as `("a", "b", "c")`.
If I intend to allow all files, I can just use `"*"`.

This may not be the most elegant solution (Not a fan of using code as "configuration"). Ideally, the blog is not saturated of dirs and files other than static content... But what do I know?

### Considerations

1. The year indexes are autogenerated. They will parse the month_year timestamp in the name of the file and sort their list using it. Anything under posts will be included as long a the title uses an `H3` header format and it is the first line in the document (markdown comments are accepted too).
2. Any file at root level or within another dir, e.g. `example/index.md` will have no footer unless it is annotated in it. If included, the footer will include tracking and an anchor pointing to the landing page.
3. There is no direct map between the dropdown menu and the pages beyond the `Posts`. If you add a new page and want it in the menu, you need to add a new entry in the `menu.html.j2` template.
4. The current build in the Jenkinsfile completes by publishing to [Neocities](https://neocities.org), you may opt to push to a different site or just use Codeberg pages, adapt the step accordingly
5. An atom feed is generated everytime this builds. The feed will only add entries for the `Posts`.

### Annotations

Files may contain some comments that will alter their behavior. In a similar manner all files (markdown) are parsed twice unless explicitly avoided, this, to allow injecting tags and `jinja` logic. This way the parsing workflow is as follows:

```
markdown file --> html file with jinja tags --> html static file
```

The available annotations at this time are:

* `<!-- NAV_MAIN -->` indicates that the redirection link points to the landing page
* `<!-- NO_PROGRESSBAR -->` indicates that the page will not render a scroll progressbar
* `<!-- NO_RENDER -->` indicates that no `jinja` rendering is needed
